## Persistencia: Cloud Firestore con firebase-admin
- La base es Cloud Firestore (modo nativo). El package.json ya trae firebase-admin 14: nada de Knex, SQL, el SDK web (firebase/firestore) ni otras librerías de datos.
- config/database.ts (FIJO): `db` (Firestore de firebase-admin, ya inicializado contra el emulador en desarrollo) y `closeDatabase`. Nunca initializeApp, getFirestore ni credenciales en un módulo. shared/db (FIJO): newId() (uuid), withId(snapshot), toIsoDateTime, toIsoDate, toTimestamp, nowTimestamp, toMoney, countOf(query), prefixRange(texto) y createWithNextCode(colección, prefijo, (code) => documento).
- Persistencia SIEMPRE en Firestore (nunca datos dummy ni arreglos en memoria). El backend NO carga datos de ejemplo ni declara índices: son de la capa database (scripts de firestore/seeds y firestore.indexes.json).
  - Con DATA.databaseContract: usa EXACTAMENTE sus colecciones y campos (DATA.databaseFiles: docs/collections y los scripts de carga).
  - Con DATA.designDatabase (la base todavía no existe): tú diseñas las colecciones en el tipo de documento de cada repositorio (colecciones en inglés, camelCase y plural; campos camelCase) y la capa database las carga después a partir de ellos.
- shared/auth autentica contra la colección users (email en minúsculas, passwordHash bcrypt, name, role, active, createdAt; id del documento = id del usuario). Si un módulo guarda quién hizo algo, guarda el id del usuario en un campo {accion}ById, nunca el nombre.
- {modulo}.repository.ts: una interface {Entidad}Document por colección con los campos EXACTOS en camelCase (sin el id), `export type {Entidad} = {Entidad}Document & { id: string }` y `export const {COLECCION}_COLLECTION = { collectionName: '{coleccion}' } as const` por colección (la capa database lee ese nombre). Devuelve documentos con su id (withId o { ...doc.data(), id: doc.id }).
- Consultas: db.collection(COLECCION).where(campo, '==', valor).orderBy(campo, 'desc').offset(offsetOf(query)).limit(query.size); el total con countOf(consulta sin offset ni limit). Firestore no tiene "contiene" ni LIKE: la búsqueda de texto es por prefijo de un campo (prefixRange) y entonces se ordena por ese campo. Filtrar por un campo y ordenar por otro necesita un índice compuesto: nómbralo en un comentario del repositorio.
- Ids: newId() en el service al crear y collection.doc(id).create(documento) (nunca .add()). Un dato único (código, SKU, email) se valida con una consulta where antes de crear o editar.
- Código visible correlativo que asigna el sistema (legajo, número de factura, de ticket, de pedido): NUNCA un uuid ni un contador en memoria ni count()+1. El repositorio crea el documento con createWithNextCode(COLECCION, 'E-', (code) => ({ ...documento, campoCodigo: code, createdAt: nowTimestamp() })): el id del documento es el código (E-0001, E-0002…, el mismo formato que los datos de la capa database) y el service recibe el documento creado.
- Fechas: los momentos y los campos que se ordenan o filtran por fecha se guardan como Timestamp (nowTimestamp, toTimestamp) y se devuelven con toIsoDateTime; una fecha sin hora puede guardarse como string 'YYYY-MM-DD'. Lo opcional sin dato va como null, nunca undefined.
- Varias escrituras que van juntas: db.runTransaction(async (trx) => { … }) (lecturas antes que escrituras) o db.batch() si no hace falta leer.
- El service mapea documento → DTO (null → '' o null según el DTO, toMoney, toIsoDateTime, toIsoDate).
